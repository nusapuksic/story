---
name: spec-guard
description: 'Provides a workflow to keep bug fixes and feature plans aligned with docs/cli-spec.md invariants and architecture boundaries.'
---
Use this skill when planning or implementing changes that could affect core behavior, import logic, persistence, identifier policy, or LLM integration.

1. Read the requested change and map it to relevant sections of `docs/cli-spec.md`.
2. Identify affected invariants (deterministic import, canonical project folder, rebuildable SQLite projection, and untrusted LLM output handling).
3. Check package boundaries and dependency direction:
   - CLI handlers call application services.
   - Application services call domain logic.
   - Adapters (store/import/provider) stay behind interfaces.
4. Validate identifier ownership:
   - IDs must be generated by deterministic code.
   - LLM output must never invent persistent IDs.
5. Validate import behavior:
   - ambiguous order/boundaries must fail with actionable recovery;
   - no partial canonical mutation on failed import;
   - preserve original source files.
6. Validate model-output safety:
   - treat LLM responses as untrusted candidates;
   - require valid paragraph evidence identifiers for concrete claims;
   - reject malformed or unsupported output from accepted state.
7. Require tests for behavior changes, especially around determinism, failure modes, and no-partial-write guarantees.
8. Produce a short compliance note in the implementation plan:
   - which invariants are touched;
   - how each is preserved;
   - any deliberate, justified deviation.

Guardrails:
- Prefer the smallest design that preserves spec invariants.
- Do not trade determinism for convenience.
- If a proposed change conflicts with `docs/cli-spec.md`, stop and surface the conflict explicitly.
